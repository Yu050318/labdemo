# LabFlow 跨部门执行计划（V1.2）

> 制定日期：2026-07-29  
> 需求与技术基线：`LABFLOW_PRD_AND_TECH_STACK.md` V1.2  
> 计划性质：产品、设计、开发、测试四部门协作计划，不包含代码实现  
> 当前范围：优先完成个人实验人员使用的 P0，并为 P1 本地桌面 Worker、P2 团队版预留扩展空间

## 1. 项目目标

将 LabFlow 首先交付为面向个人实验人员的响应式 Web 应用，完成“安排实验—调用人工维护的实验方案—准备器材—执行步骤—计时提醒—完成归档—晚间汇总”的闭环。

P0 技术基线：

- 前端：Next.js、React、严格 TypeScript、响应式 PWA。
- 部署：Sites 优先，Vercel 作为兼容性备用方案。
- 后端：Supabase PostgreSQL、Auth、RLS、Cron。
- P0 不包含：文档解析、PDF/OCR、AI 方案提取、联网文献比较、Python Worker、Docker、团队协作。

后续演进：

- P1：增加本地桌面 Python Worker、文档处理、至少三来源比较、材料库、仪器与场地预约。
- P2：增加团队空间、角色权限、云端 Worker 选项、Zotero 与机构系统集成。

## 2. 部门角色与边界

| 部门 | 核心职责 | 主要交付物 | 不负责 |
|---|---|---|---|
| 产品部 | 明确目标、范围、优先级、业务规则、验收标准和版本决策；协调跨部门依赖 | PRD、版本范围、业务流程、验收标准、决策记录、发布结论 | 编写代码、制作具体 UI 稿、替代测试部执行质量判定 |
| 设计部 | 将已确认的需求转化为信息架构、页面流程、交互状态和响应式视觉事实来源 | 页面清单、用户流程、线框/高保真稿、组件与状态规范、设计验收记录 | 擅自改变产品范围、决定后端实现、编写业务代码 |
| 开发部 | 在 PRD 和设计事实来源基础上完成技术规格、数据模型、接口、实现、部署和工程验证 | Tech Spec、API Contract、数据库/RLS 方案、可运行版本、部署说明、自动化检查结果 | 擅自改变业务目标或验收口径、代替产品做范围决策 |
| 测试部 | 提前制定质量策略，验证功能、权限、时间、离线、兼容性、视觉和发布质量 | 测试计划、用例、缺陷单、回归报告、发布质量结论 | 修改需求口径、绕过未解决的高风险缺陷批准上线 |

## 3. 协作原则

1. `LABFLOW_PRD_AND_TECH_STACK.md` 是需求与技术范围的当前事实来源；变更必须由产品部记录并通知三部门。
2. 开发部先建立 API Contract、数据模型和权限边界，再进入真实数据集成。
3. 设计部先交付可验证的视觉事实来源；开发部先用固定数据完成静态页面，截图验收通过后再接入真实数据。
4. 测试部从需求冻结阶段介入，不在开发结束后才开始准备测试。
5. 任何部门发现需求冲突、安全风险或无法验收的描述，应提交产品部裁决，不自行假设并扩大范围。
6. P0 未达到发布门槛前，不并行实施 P1 文档处理或 Worker，以免分散首版闭环资源。

## 4. P0 阶段执行计划

### 阶段 P0-0：需求补全与版本冻结

**负责人：产品部**  
**参与：设计部、开发部、测试部**

产品部：

- 确认 P0 功能清单及明确排除项。
- 冻结核心用户流程和业务规则。
- 补齐下列发布前决策：
  - 提醒服务承诺为“尽力分钟级送达”，不承诺危险实验的闹钟级可靠性。
  - 短时离线支持的具体操作范围。
  - 支持的浏览器与最低版本，特别是 iOS PWA/通知限制。
  - 登录方式、账户删除和数据保留规则。
  - 晚间汇总时间、用户时区和旅行改时区规则。
  - JSON/CSV 导出范围。
- 建立需求变更记录和风险清单。

设计部：

- 审查用户流程是否存在缺页、缺状态或不可操作环节。
- 输出需要产品确认的交互问题，不开始具体视觉稿。

开发部：

- 审查 Sites、Next.js 与 Supabase 的边界和兼容性。
- 提交数据、权限、提醒、离线和部署方面的待确认事项。

测试部：

- 将验收标准转化为可测试条件。
- 标记时间、权限、跨设备、离线、通知降级等高风险场景。

**完成条件（G0）：**

- 产品部发布 P0 冻结版需求。
- 所有 P0 功能均有验收标准。
- 未决事项有负责人、截止门槛和默认处理原则。

### 阶段 P0-1：产品流程与设计交付

**负责人：设计部**  
**审批：产品部**  
**评审：开发部、测试部**

设计部交付：

- 信息架构与导航结构。
- 页面清单及每页目标。
- 核心流程：
  - 注册/登录与首次设置。
  - 早、中、晚日程安排。
  - 手工创建或关联实验方案。
  - 器材准备清单。
  - 实验步骤勾选、跳过和备注。
  - 多计时器及提醒状态。
  - 实验完成、归档和历史查看。
  - 晚间汇总与次日任务。
  - 设置、通知权限、导出和异常恢复。
- 桌面端与移动端的响应式布局规则。
- 空状态、加载、失败、离线、冲突、权限拒绝和通知不可用状态。
- 可访问性要求，包括键盘操作、焦点态、语义标签和对比度。
- 视觉事实来源、设计组件状态和交付标注。

产品部：

- 验证设计是否覆盖业务流程和验收标准。
- 对新增需求建议做版本判断，避免设计过程扩大 P0。

开发部：

- 评估设计状态是否可实现、可复用和可测试。
- 确认响应式断点、组件状态和数据字段是否完整。

测试部：

- 基于设计稿补充视觉、交互和异常状态用例。

**完成条件（G1）：**

- 产品部确认流程与范围一致。
- 开发部确认交付信息足以实现。
- 测试部确认关键状态均可验证。

### 阶段 P0-2：技术规格与测试设计

**负责人：开发部（技术规格）、测试部（测试设计）**  
**审批：产品部**

开发部交付：

- P0 Tech Spec 和模块边界。
- API Contract 或等价接口事实来源。
- 数据模型与迁移顺序，至少覆盖：
  - 用户与个人空间。
  - 日程与实验执行记录。
  - 方案及不可变版本。
  - 准备清单与步骤执行。
  - 多计时器与计时事件。
  - 通知任务、站内通知和晚间汇总。
  - 审计与导出需要的数据。
- Supabase Auth、RLS、权限负向规则和服务端写入边界。
- 提醒、时区、幂等、并发、离线 outbox 和冲突处理方案。
- Sites 部署兼容性结论、环境隔离和回退方案。
- 监控、日志、备份和恢复要求。

测试部交付：

- P0 总体测试计划。
- 需求到测试用例的追踪矩阵。
- 功能、权限、RLS、时间、时区、跨午夜、离线、跨设备、通知降级、导出、兼容性和响应式测试集。
- 发布阻断缺陷等级和回归范围。
- 测试数据及隐私处理规则。

产品部：

- 只审批技术方案是否满足业务目标、成本约束和验收标准，不指定代码实现。

设计部：

- 确认技术状态模型可支持已交付的界面状态。

**完成条件（G2）：**

- 技术规格、测试计划和设计状态之间无未解决冲突。
- 安全、权限、计时和通知降级均有明确验证方法。
- Sites 不兼容风险已有验证任务和 Vercel 回退条件。

### 阶段 P0-3：静态页面与视觉验收

**负责人：开发部**  
**验收：设计部**  
**参与：产品部、测试部**

开发部：

- 依据设计事实来源，以固定代表性数据完成桌面端和移动端静态页面。
- 完成所有关键页面状态，不接入真实 Supabase 数据。
- 提供可重复的页面预览和截图。

设计部：

- 检查布局、层级、间距、文字溢出、图片/图标、响应式、交互状态和可访问性。
- 输出明确的设计验收结论。

测试部：

- 执行基础响应式、浏览器和可访问性检查。

产品部：

- 验证页面表达没有偏离业务目标或遗漏 P0 流程。

**完成条件（G3）：**

- 桌面端和移动端静态保真通过。
- 无文字截断、重叠、关键操作遮挡或核心状态缺失。
- 设计部批准进入真实数据集成。

### 阶段 P0-4：功能实现与集成验证

**负责人：开发部**  
**持续验证：测试部**

开发部按依赖顺序交付：

1. 认证、个人空间和 RLS。
2. 日程与早/中/晚安排。
3. 手工实验方案库、版本与方案关联。
4. 器材准备清单和实验步骤执行。
5. 多计时器、站内提醒和 Web Push 降级。
6. 完成归档和执行历史。
7. 晚间汇总与次日任务。
8. 短时离线、冲突提示和幂等重放。
9. JSON/CSV 导出。
10. 日志、监控、备份恢复和部署配置。

每个功能增量必须同时提供：

- 与需求对应的完成说明。
- 自动化测试或等价验证证据。
- 权限与异常路径验证。
- 对测试部已报缺陷的处理状态。

测试部：

- 按增量执行冒烟、功能、权限和回归测试。
- 高风险缺陷及时反馈，不等待全部功能完成。

设计部：

- 对接入真实数据后的页面进行二次视觉检查。

产品部：

- 进行阶段性业务验收，控制范围变更。

**完成条件（G4）：**

- P0 功能闭环可以使用代表性账户完整走通。
- RLS 负向测试、时间专项和关键端到端流程通过。
- 无阻断级或高严重度未解决缺陷。

### 阶段 P0-5：发布候选与试点

**负责人：测试部（质量结论）、开发部（候选版本）**  
**发布批准：产品部**

开发部：

- 生成 staging 发布候选版本。
- 完成 Sites 部署验证；若触发已定义回退条件，则使用 Vercel 备用方案。
- 验证生产迁移、环境变量、监控、备份和恢复流程。

测试部：

- 完成全量回归、浏览器/移动端、视觉、安全、性能基线和恢复演练。
- 输出发布测试报告和遗留风险。

设计部：

- 完成最终桌面端、移动端和关键状态视觉验收。

产品部：

- 组织小规模个人实验人员试点。
- 核对成功指标、用户反馈和遗留风险。
- 决定发布、限量发布或退回整改。

**完成条件（G5）：**

- 核心闭环、权限隔离、计时恢复、通知降级、导出和备份恢复均通过。
- 用户已被明确告知 Web Push 的能力边界。
- 所有遗留问题有风险等级、负责人和版本归属。

### 阶段 P0-6：正式发布与复盘

**负责人：产品部**  
**参与：设计部、开发部、测试部**

- 产品部确认上线范围、发布说明和指标看板。
- 开发部执行已审批的正式部署并观察监控。
- 测试部执行生产冒烟并确认核心流程。
- 设计部检查生产环境的关键页面。
- 四部门共同复盘试点与上线数据，形成 P0.1 修正清单和 P1 是否启动的决策。

**完成条件（G6）：**

- 生产环境核心流程可用，监控与告警正常。
- P0 发布结论、已知限制和后续清单完成归档。

## 5. P1 阶段计划：本地桌面 Worker 与扩展能力

P1 只能在 P0 稳定且产品部重新冻结范围后启动。

### 产品部

- 明确优先支持的桌面平台，建议先验证 Windows，再决定 macOS。
- 确认允许处理的文件格式、大小、数量和隐私边界。
- 定义“至少三个独立来源”的计数、去重、冲突和不足三份时的展示规则。
- 定义 AI 生成内容的人工确认粒度和版本规则。
- 确认本地模型或第三方模型 API 的费用、隐私和数据保留边界。
- 冻结材料库存、仪器/场地预约的业务规则。

### 设计部

- 设计本地 Worker 的安装、登录、连接、运行、暂停、更新和错误恢复流程。
- 设计 Web 端的处理任务状态、来源证据、三方案比较、人工复核和结果入库流程。
- 设计材料登记、使用、时间确认、归档及库存异常状态。
- 设计仪器/房间登记、预约和提醒流程。

### 开发部

- 交付本地桌面 Worker 技术规格、安装包、签名、升级和卸载方案。
- Docker 仅用于开发、测试、CI 和可选实验室服务器部署，不要求普通用户安装。
- Worker 使用用户范围、可撤销、最小权限凭据，不使用全局高权限密钥。
- 完成私有文件存储、任务队列、PDF/OCR、结构化提取、来源追溯和结果同步。
- 保证本地临时文件清理、传输加密、错误恢复和任务幂等。

### 测试部

- 验证全新安装、升级、卸载、崩溃恢复、电脑休眠、断网、磁盘不足和权限异常。
- 验证 Worker 未运行时任务状态清晰且不会丢失。
- 验证文件和凭据不被其他账户越权访问。
- 以固定语料验证字段准确率、来源定位、缺失参数、冲突呈现和三来源规则。
- 验证材料与预约功能的业务规则和归档准确性。

### P1 发布门槛

- 普通用户无需安装 Python、Docker 或配置环境变量。
- 用户电脑关闭或 Worker 未运行时，系统明确显示等待状态，不虚假承诺后台完成。
- 来源证据可追溯，AI 不得把未出现的参数当作确定事实。
- 安装包、更新机制、凭据存储和文件清理通过安全验证。

## 6. P2 阶段计划：团队与商业化扩展

### 产品部

- 定义团队角色、资源归属、成员离开、所有权转移和审计规则。
- 决定云端 Worker 的收费、额度、隐私和本地 Worker 共存策略。
- 定义 Zotero 与机构预约系统的业务范围。

### 设计部

- 设计个人空间与团队空间切换、成员管理、权限提示、共享与审计体验。
- 设计本地/云端处理模式的选择、费用和隐私说明。

### 开发部

- 在现有 `space_id + membership` 边界上开放团队权限。
- 增加云端 Worker 选项、Zotero 连接器和机构系统适配层。
- 保持外部同步幂等、可重试并可人工恢复。

### 测试部

- 重点验证跨租户隔离、角色越权、所有权转移和成员退出。
- 验证本地/云端任务切换、外部系统失败和重复同步。

## 7. 关键交付物与审批关系

| 交付物 | 主责 | 审批/确认 | 完成标准 |
|---|---|---|---|
| PRD 与版本范围 | 产品部 | 产品部负责人 | 目标、范围、规则、验收、排除项完整 |
| 页面流程与视觉事实来源 | 设计部 | 产品部；开发/测试会签 | 页面、状态、响应式和交互可实现可测试 |
| Tech Spec 与 API Contract | 开发部 | 产品部确认业务一致性 | 数据、权限、接口、异常和部署边界明确 |
| 测试计划与追踪矩阵 | 测试部 | 产品部；开发会签 | 每项验收标准均有测试覆盖 |
| 静态页面版本 | 开发部 | 设计部验收 | 桌面/移动静态保真通过 |
| P0 功能候选版本 | 开发部 | 测试部质量确认 | 核心流程、自动化检查和安全验证通过 |
| 正式发布决定 | 产品部 | 四部门提供证据 | 发布门槛满足，遗留风险已接受并归档 |

## 9. 风险责任分配

| 风险 | 主责部门 | 协作部门 | 控制要求 |
|---|---|---|---|
| P0 范围持续膨胀 | 产品部 | 全部 | 变更必须记录版本归属和影响 |
| Web Push 不能硬实时送达 | 产品部 | 开发、测试、设计 | 明确承诺边界、站内补显、降级提示 |
| 时区/跨午夜导致重复或漏提醒 | 开发部 | 测试部 | IANA 时区、幂等键、时间专项测试 |
| RLS 错误造成数据泄露 | 开发部 | 测试部 | 默认拒绝、负向权限测试、最小权限 |
| 离线或双设备覆盖数据 | 开发部 | 测试、设计 | revision、幂等事件和可理解的冲突提示 |
| 响应式页面状态缺失 | 设计部 | 开发、测试 | 先定义状态，固定数据截图验收 |
| Sites 与运行时不兼容 | 开发部 | 产品部 | P0-2 验证；按条件回退 Vercel |
| P1 本地 Worker 对普通用户过于复杂 | 设计部 | 产品、开发、测试 | 安装包化、无命令行、可恢复错误提示 |
| AI 参数幻觉或错误合并来源 | 产品部 | 开发、测试 | 来源定位、待复核、固定语料门槛 |

## 10. 项目跟踪规则

- 状态统一使用：未开始、进行中、待评审、被阻塞、已完成。
- 每项工作必须标注主责部门、输入、输出、依赖和完成条件。
- 阻塞超过一个协作周期时，由产品部组织决策并记录结论。
- 需求变更至少记录：变更原因、影响版本、影响部门、验收变化和批准人。
- 不以“代码完成”作为功能完成；必须同时满足设计、测试和产品验收。
- 在人员配置和可用时间确认前，本计划不承诺具体日期；排期由各部门拆解工作量后共同形成。
